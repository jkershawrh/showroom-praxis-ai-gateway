= Track 2: Define failure and recovery behavior

Centralizing model access also centralizes failure. Platform owners must decide how clients experience timeouts, unavailable backends, and configuration errors instead of allowing every application to improvise a different retry policy.

== What you will learn

* Distinguish gateway readiness from backend success
* Observe a controlled unavailable-backend response
* Recover by restoring declarative configuration

== See: Failures cross ownership boundaries

image::architecture.svg[Gateway failure boundary between applications and the selected model backend,link=self,window=_blank]

OpenShift readiness answers whether the Praxis listener can serve traffic. It does not guarantee that a remote model is healthy for every request. Conflating those conditions can restart a healthy gateway during an upstream incident.

The UI catches connection-level errors and returns an explicit `gateway_connection_error` with the request trace identifier. HTTP failures remain visible as statuses and sanitized bodies. Neither path should expose the upstream credential.

The base manifest is declarative. If a learner changes backend configuration, reapplying Kustomize restores the reviewed state. In a production platform, OpenShift GitOps would continuously reconcile the same intent and record drift.

Retry behavior is deliberately not hidden in this exercise. Retrying generative requests can increase cost or duplicate side effects, so it requires an application-specific decision.

== Do: Exercise a controlled failure

=== Step 1: Preserve the current network policy

Export the gateway egress policy before introducing a temporary fault.

[source,bash,role="execute",subs="attributes+"]
----
oc -n {project_name} get networkpolicy praxis-ai-allow-required-traffic -o yaml >/tmp/praxis-egress-before.yaml
----

This file provides immediate recovery if GitOps reconciliation has not yet run.

=== Step 2: Block the backend network path

Temporarily remove allowed egress from the Praxis pod. Praxis remains ready, but its configured external backend becomes unreachable.

[source,bash,role="execute",subs="attributes+"]
----
oc -n {project_name} patch networkpolicy praxis-ai-allow-required-traffic \
  --type=merge -p '{"spec":{"egress":[]}}'
oc -n {project_name} get deployment praxis-ai -o jsonpath='{.status.availableReplicas}{" gateway replica remains available\n"}'
----

The gateway deployment should remain available even though inference cannot complete.

=== Step 3: Send a request

Invoke the same stable client contract and retain the non-success evidence.

[source,bash,role="execute",subs="attributes+"]
----
cd ~/praxis-lab
python3 clients/python/client.py || true
----

Observe that the failure occurs at the backend hop rather than requiring a different client endpoint.

=== Step 4: Reconcile the reviewed state

Restore the policy captured before the fault.

[source,bash,role="execute",subs="attributes+"]
----
oc -n {project_name} replace -f /tmp/praxis-egress-before.yaml
oc -n {project_name} get networkpolicy praxis-ai-allow-required-traffic
----

The restored policy allows the reviewed HTTPS and DNS egress paths again. OpenShift GitOps will also reconcile this resource back to the declared state.

=== Verify

Send the request again and rerun validation.

[source,bash,role="execute",subs="attributes+"]
----
cd ~/praxis-lab
python3 clients/python/client.py
PROJECT_NAME={project_name} python3 runtime-automation/track1/validate.py
----

The client response and validator should both return to green.

== Key takeaway

Gateway readiness, backend reachability, and request success are related but distinct signals. Explicit failure evidence and declarative recovery give platform teams predictable behavior without coupling clients to providers.
